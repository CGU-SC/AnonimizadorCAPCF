Antes da primeira mudança

Começar o seu histórico

A pasta chega sem histórico do git. Comece o seu antes de mudar qualquer coisa: é ele que deixa voltar atrás e mostra, depois, o que cada mudança fez.

  1. Ligar o histórico na raiz do projeto
    PowerShell
    git init
  2. Conferir o que vai entrar
    PowerShell
    git status

    Nada de .env, preferencias.ini, .venv nem builds pode aparecer: o .gitignore os deixa de fora. Se aparecer, pare e descubra por quê antes do primeiro commit — o que entra num commit fica em todo clone para sempre, mesmo apagado depois.

  3. Gravar o ponto de partida
    PowerShell
    git add .
git commit -m "Anonimizador CAPCF - versão 0.2.0, como recebida"

O método

O caminho de uma mudança

O programa inteiro foi construído assim, e é o que manteve as regras e o código dizendo a mesma coisa. Mudança pequena pula passos; nenhuma pula o 4 e o 5.

  1. Achar a regra

    Na aba Regras, o assunto e a spec. Se o pedido bate numa regra dura, ele volta para conversa antes de virar código.

  2. Mudar a spec antes do código

    Uma emenda datada, com o porquê. RN nova continua a numeração da spec, e um número nunca volta a ser usado: a regra que sai fica escrita como retirada, com a data (como a RN-66 da spec 004), porque o código antigo e as revisões ainda a citam. A regra mudada leva a nota da emenda.

  3. Desenhar a tela, se ela muda

    Um rascunho novo em mockups/, na pasta da área, com o número seguinte — nunca por cima do anterior —, nos dois temas, com as cores do mockups/sistema-de-design.md. Cor nova entra no sistema de design e no programa/estilo.py, e em nenhum outro lugar.

  4. Código e teste juntos

    O teste prova a regra, não a linha. Defeito consertado ganha o teste que o teria pegado, para ele não voltar calado.

  5. A lista inteira dos testes

    Toda, e não só a do arquivo mexido: as peças se usam umas às outras.

  6. Conferir na tela

    Feche e abra o programa — ele não recarrega o código sozinho —, e faça o caminho normal e o torto: o arquivo vazio, o que não abre, o motor faltando, a janela estreita. Teste não vê tela, e a maior parte dos defeitos deste programa só apareceu olhando.

  7. Revisar por um ângulo

    Releia a mudança procurando um tipo de defeito por vez: quebra, dado gravado errado, resultado errado sem aviso. Foi essa releitura que achou, na construção, CPF escapando inteiro e arquivo bom sendo recusado.

  8. Gravar e atualizar o backlog

    Um commit por assunto. A situação da funcionalidade vai para o especificacoes/backlog.md.

ℹ

Meça antes de mudar o que depende de desempenho. O PaddleOCR só virou padrão depois de medido contra o Tesseract nas mesmas páginas, e o que se pede à IA foi medido com uma página cheia (aba Armadilhas). Mudança que parece barata, e não é, só aparece medindo.

Windows e Linux no mesmo projeto

A quebra de linha

Os arquivos do projeto não usam todos a mesma quebra de linha: a maioria dos .py usa a do Windows, alguns a do Linux, e o git do Windows (com core.autocrlf) converte na entrada e na saída. Por isso o git diff não acusa quando uma ferramenta troca a quebra do arquivo inteiro.

  • Edite pelo editor, que mantém a quebra que o arquivo já tem. O sed -i do Git Bash regrava o arquivo inteiro com a quebra do Linux, calado.
  • O > do PowerShell reescreve o que passa por ele, com outra codificação e outra quebra. Para olhar os bytes de um arquivo de outra versão, use o Bash: git show <versão>:arquivo | od -c.
  • Para conferir, conte no Python os \r\n nos bytes do arquivo. O grep do Git Bash conta toda linha como do Windows, também num arquivo todo do Linux.
  • O .gitattributes marca os PDFs como binários: os da massa existem para serem exatos, e o git não pode "arrumá-los".
